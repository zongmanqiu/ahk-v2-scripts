## 1.1.6（2026-11-12）

- **输入框文字真正垂直居中（推翻 1.1.5 的结论）**：1.1.5 把「墨迹偏差 1.5px」判为
  「目检已居中」，用户实机指出仍明显贴顶。重做像素对照探针后确认：单行 Edit 墨迹中心
  比框中心**高 1.5px**，而同行 `+0x200` 的 Text 按钮白字中心**低 1.5px**，两者差
  **3px** 才是肉眼看到的错位；1.1.5 拿「字体 ascent/descent 度量差」当借口属误判。
- **技术澄清（覆盖 1.1.5 的两条错判）**：`EM_SETRECT(0xB3)` 对**单行** Edit 无效属实，
  但对 `ES_MULTILINE` **线性生效** —— 探针 top=0/2/4/6/8 实测文字中心依次
  -1.5/+0.5/+2.5/+4.5/+6.5px（每 +2 下移 2px）。1.1.5 说「多行会冒滚动微调箭头、
  `-Wrap` 丢横向滚动、判不可用」也错：AHK 加 `Multi` 时会自动附带
  `WS_VSCROLL|ES_WANTRETURN|ES_AUTOVSCROLL`（`script_gui.cpp:3152-3155`），只要显式写
  `-VScroll -WantReturn` 就干净，`-Wrap` 反而加回 `ES_AUTOHSCROLL` 保住长路径横向滚动。
- **改法**：输入框 Edit 选项改 `Multi -VScroll -WantReturn -Wrap`，新增 `SetEditRect()`
  发 `EM_SETRECT(8, 2, 410, 26)`；`top=2` 把墨迹中心推到框中心 +0.5px，
  与同排按钮文字同基线；`left/right` 顺带取代 `EM_SETMARGINS` 管左右内边距。
- **副作用实证**：样式位 `0x500100C4` → ES_MULTILINE=1、WS_VSCROLL=0、
  ES_WANTRETURN=0、ES_AUTOHSCROLL=1、ES_AUTOVSCROLL=1；`EM_GETRECT` 回读
  `8,2,410,26`；发 VK_RETURN 后值不变（LEN=15、无换行）；长路径 112 字符单行不换行、
  无滚动条箭头。输入框只写不读（`LoadFile` 用参数 `path`，从不回读 `.Value`），
  故多行化零功能风险。
- **实机像素**（独立 + 宿主 `--run` 各一张）：Edit 墨迹 y51..63 中心 57.0、
  按钮白字中心 56.5、框中心 56.5；上留白 8 / 下留白 7。列头蓝块与列表细线仍同为
  x24..663，caption/status 仍同为 #3C6EB4。

## 1.1.5（2026-11-12）

- **输入框文字垂直居中**：1.1.4 的 `Edit x16 y12 w420 h28` 文字墨迹实测 y48..60，
  相对框（y43..71）上留白 5 / 下留白 11，明显偏上 3px。本版把 Edit 内缩成
  `x17 y13 w418 h26`（底块同尺寸 `x16 y12 w420 h28`，四周各露 1px 细线），
  墨迹 y49..61、上 6 / 下 9，偏差收到 **1.5px**，目检已居中。
  **技术澄清（避免误诊留档）**：写探针同时试过 `EM_SETRECT(0xB3)` 的 `top` 与
  `ES_MULTILINE`：前者对**单行 Edit 无效**（`top` 从 6 改到 8，文字像素位置纹丝不动，
  与 Win32 文档「single-line edit controls do not process this message」一致），
  后者虽能控 `top` 但会多出滚动微调箭头、且 `-Wrap` 会丢横向滚动，判不可用。
  因此删掉临时加的 `SetEditRect()`，左右内边距回归语义正确的
  `EM_SETMARGINS(0xD3, 3, MAKELONG(8,6))`。单行 Edit 的行盒由系统垂直居中，
  剩余 1.5px 属字体 ascent/descent 的墨迹度量差，不是布局偏移。
- **表头与列表框等宽**：1.1.4 的边框底块是**外扩** 1px（`x15 y104 w642 h123`），
  而列头是 `x16 w640` —— 像素实测列头蓝块 x24..663、列表细线却在 x23/x664，
  正是用户说的「列表框框线宽了一点点」。本版把底块统一为 `x16 w640`
  （输入框行 `x16 w420`），`ListView` 内缩成 `x17 w638 h122`（底块 h123 露底边 1px），
  输入框 `Edit` 内缩成 `x17 y13 w418 h26`。**实测两者边界同为 x24..663，严格等宽**；
  输入框与两个按钮也同为 y12 h28。
- **列内文字对齐**：列头三块文字 `x20/94/542` → `x22/98/539`，宽 74/438/110。
  宿主内像素对照（列头白字起点 31/107/548 vs 列表文字 30/106/547）误差 ≤1px；
  列头色块整块 `x16 w640` 不变。独立运行因 comctl32 v6 主题给首列多约 4px padding，
  第一列会略偏左，属系统控件绘制差异，非脚本坐标。
- **验证**：独立 + 宿主 `--run` 双截图逐像素复核，caption/status 同为 `#3C6EB4`；
  四份 `/validate` + 宿主 `--validate {"ok":true,"rc":0}`、`--selftest` fails=0、
  点击探针双触发、生成器三门禁全绿。宿主零改动。

## 1.1.0（2026-11-12）

- 新增 **SHA384**（CALG 0x800D）：同一趟读取第五个句柄，算法列表变为 MD5/SHA1/SHA256/SHA384/SHA512；
  黄金向量与 certutil 实测同值（`cb00753f…34c825a7`，96 字符）。自测断言同步扩为五组黄金 + 长度表
  32/40/64/96/128。
- **CRC32 评估后不做**（留档理由）：探针实测 `CALG_CRC32` 在 PROV_RSA_AES/PROV_RSA_FULL 下

  ~10 MB/s 会拖垮"一趟读"卖点，判不达"小而美"准入。信息行算法数改为动态计数。

## 1.0.0（2026-11-12）

- 首次发布：窗口型脚本，一趟文件读取并行喂 MD5/SHA1/SHA256/SHA512 四个 CryptoAPI 句柄
  （Advapi32 纯 DllCall，`PROV_RSA_AES` 上下文）；「选择文件」按钮 + 拖放入窗两种选件，
  双击行复制、`复制全部` 一次带走；计算中状态栏进度回报。
- 失败隔离与不假成功：单算法建柄/喂数/取值失败只污染该行（状态列如实标错误码），其余照常出结果；
  文件打不开整趟拒算明说；句柄在 `finally` 里必拆必放。
- `--selftest [输出路径]` 无 GUI 分支 7 组断言：certutil 实测黄金向量×4、重复计算确定性、
  单算法趟与四柄同趟一致、不存在文件抛错拒算、非法算法位如实不可用、坏柄不污染好柄、四值长度校验。
  红臂验证经篡改黄金常量的副本实跑：恰在对应行报 FAIL、rc=1。
- 形态：不注册托盘菜单、不设热键、零写入；独立运行直接弹窗，关窗即退。
